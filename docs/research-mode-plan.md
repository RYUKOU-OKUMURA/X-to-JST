# X 調べものモード — 設計・実装計画案

作成: 2026-10-02 / 状態: ユーザーの実装継続指示に基づき初版を実装中。検証済み範囲と残件は `research-validation.md` に記録。全履歴取得や外部送信範囲の拡大は含まない。

## ゴール

Xで見つけた情報を、今の目的で拾い、あとで探し直し、新しい情報と結び付けて使えるようにする。
普段のタイムラインには常時ラベルを増やさず、必要なときだけ「調べものモード」を開く。

初版で閉じる体験:

1. 「非エンジニアでも試せるAI自動化」など目的を入力し、読み込んだ投稿から候補を拾う。
2. 選んだ投稿を保存する。「なぜ気になったか」は任意で一言残せる。
3. 後日、違う言葉で探しても関連する保存投稿を見つけ、元の投稿を開ける。
4. 今読んでいる投稿を選び、過去の保存投稿から続報・変更・具体例の候補を比較できる。

## 計画作成時の現状確認と未決事項

- `x-dom.ts` に本文・投稿日時・URLを取得する処理がある。引用の所有関係が不明なときは取得を拒否する。
- 現行の表示条件は日時パーサーに依存する。調べものの候補取得をこの条件へ通すと、時刻のない投稿が落ちるため、別の入口を設ける。
- `chrome.storage.local` は既に使用しており、backgroundでTRUSTED_CONTEXTSに制限される。現在の用途はAPIキー。投稿本文・閲覧履歴の永続保存はない。
- Jev接続、タイムアウト、認証、応答検証があるが、現在の要求と応答は日時解釈専用。新用途は新しいメッセージと検証を設ける必要がある。
- manifestにactionは未定義。現在の権限はstorage、API接続先、x.comのcontent script。
- ブックマーク・いいね・未保存閲覧のどれを優先するかは未決。「いいね、どんな設計…」は相づちであり、いいね投稿を選択した発言とは扱わない。
- 今回はコードと公式資料を確認した。現在のブラウザ設定・表示・API疎通は実測していない。既存validation文書のライブ確認は過去の証拠であり、今回の確認結果ではない。

## 初版の範囲

対象は「ユーザーが収集モードで読み込み、選んだテキスト投稿」。ブックマーク画面も候補だが、実際の利用クライアントで取得できることを最初に確認する。

- 収集開始から停止まで、現在の投稿と手動スクロールで読み込まれた投稿を一時的に集める。SPAで収集元ページが変わったら停止する。
- 収集件数・取得できなかった件数・収集元を表示。選択した投稿だけ永続保存する。
- 古いブックマークは、まずその画面で読み込む必要がある。全件取得・自動スクロール・非公開APIによる巡回は初版に含めない。
- 保存せず流れた過去投稿は、この拡張だけで遡って復元できるとはしない。今後の明示収集で残すものと区別する。
- 画像内文字、動画、リンク先全文、スレッド全体は初版の検索対象外。画面上の本文だけを扱い、その範囲を結果に表示する。
- 新機能では保存・収集の明示操作と、Jevを使う検索・関連探索の操作を分ける。通常閲覧や単なる保存ではJevへ送らない。
- JST変換の既存導線は維持する。自動通知、常時監視、クラウド同期、生成要約、ベクトルDBは初版には追加しない。

## 画面

拡張アイコンからX内の右側パネルを開閉する案。既存content scriptへ開閉メッセージを送り、Shadow DOM内で描画する。Chromeのactionを追加し、新しいUIライブラリは入れない。実クライアントで操作・レイアウトを確認して採用を確定する。

パネルの機能は3つ:

| 機能 | 入力 | 結果 |
| --- | --- | --- |
| 拾う | 今の目的＋収集した投稿 | 目的に近い投稿を並べ、選択保存 |
| 探す | 今の目的＋保存投稿 | 原文、投稿日時、保存メモ、元投稿へのリンク |
| つなげる | 選択した1投稿＋保存投稿 | 比較候補を並べ、関係の候補ラベルを表示 |

同じ検索欄と結果カードを使う。保存メモはいつでも編集できる。確率の常時表示はせず、不確かな関係は「関連候補」とする。
Escで閉じる、フォーカスを元へ戻す、キーボード操作、小さい画面で投稿を隠しすぎないことも受け入れ条件にする。

## 保存とデータの扱い

初版は既存の `chrome.storage.local` を再利用し、APIキーとは別の接頭辞付きキーで投稿ごとに保存する。独自サーバーや別DBは作らない。

保存する項目:

- 投稿ID、正規化したXの投稿URL
- 取得時点の表示本文、取得できれば表示言語と投稿日時
- 保存日時、収集元ページの種類
- 任意の本人メモ

安定した投稿IDを取得できないものは保存対象外として件数を示す。同じIDを重複登録しない。翻訳・本文変更で内容が違う再保存は差分を示し、保存メモを維持して本文更新を選べるようにする。

初版の暫定規模は200件・保存本文とメモの合計2MiB以内。一時収集にも200件・本文合計2MiBの上限を設け、到達時は収集を停止して件数と理由を表示する。これは製品側の試行上限で、ChromeやJevの仕様上限ではない。実測して見直す。超過時は理由と対象を示して止め、古い保存を勝手に削除しない。実際のストレージ書込失敗でも既存データを維持する。

一件削除、全件削除、JSON書き出し・復元を用意する。復元は形式・バージョン・ID・URL・サイズを検証し、不正入力を受け入れない。拡張削除でローカルデータを失うことを設定画面に表示する。

APIキーの入力はoptions画面、保存済みキーの取得とAPI通信はbackgroundで扱い、Xのcontent scriptへキーを返さない。研究用メッセージは研究用レコードだけを読み書きし、任意のstorageキーへアクセスできるAPIにはしない。content scriptに渡した結果本文はXページと同じ信頼境界になるため、Shadow DOMを秘密の保管場所とは扱わない。本人メモのJev送信は既定OFFとし、使う場合だけ明示的に含める。

## Jevの役割と検索の流れ

| 判断 | 実装案 | 表示の限界 |
| --- | --- | --- |
| 目的と投稿の関連度 | 投稿ごとに同じ基準のScore | 実際の有用性は本人の評価で検証 |
| 現在の投稿と保存投稿の関係 | Choiceで続報・変更・具体例・同じ話・無関係・不明 | 変更の事実や現在の利用可否を保証しない |

Jevは自由な要約文を生成する役ではない。原文・日付・メモを表示し、コードで並べ替え、固定ラベルを付ける。APIのconfidenceを正答率と呼ばない。無理に上位候補を「関連あり」とせず、該当なし・不明を出せるようにする。

処理:

1. 対象（収集中／保存済み）と件数を表示し、ユーザーが検索を開始する。目的と対象本文がTypeSafeへ送られることを操作付近に示す。
2. 初版の最大200件はキーワードだけで事前除外せず、選んだ範囲の全件を小さなバッチで判定する。意味が近いが語句が違う投稿を落とさないため。
3. バッチは最大20件を仮置きし、本文量にも上限を設ける。実APIの制限・速度・費用を測って確定する。質問ごとに対象投稿を明示する。
4. 「つなげる」も選んだ1投稿と各保存投稿を比較する。保存投稿同士の総当たりはしない。
5. 結果は進捗付きで表示。中断でき、失敗や未処理を「無関係」と混ぜない。検索条件の変更・本文更新・削除後に古い応答を反映しない。
6. 同一セッションの目的・本文・判定ルールが同じなら結果を再利用する。永続的な推論キャッシュは初版では作らない。
7. キー未設定・API障害でも保存と通常の文字列検索は使える。意味検索が実行されていないことを明示する。

## コード構成

既存の `x-dom.ts`、APIキー設定、background入口、TypeScript・Vanilla DOM・esbuild・Vitestを使う。
日時計算は変更しない。機能名で分けた小さな研究用UI・保存・Jev判定モジュールを追加し、汎用エージェント基盤は作らない。

```text
Xの表示本文 ── 明示収集 ── 調べものパネル
                                │
                                ├─ 選択保存 ── background ── chrome.storage.local
                                │
                                └─ 検索・関連探索 ── background ── Jev
                                                        │
                                    原文・関係候補・並び順を返す
```

DOM・メッセージ・保存復元・API応答はすべて検証境界。投稿内容は命令として扱わず、描画はtextContentを基本とする。
送信元の拡張ID・X origin、要求型、ID、文字数、件数、URL、返された候補IDと数値を検証する。任意URLへの取得や任意storage操作は受け付けない。

## 実装順と各工程の終了条件

各工程で、対象実装 → 対象テスト → 独立サブエージェントレビュー → 必要な修正 → コミットまで閉じる。実装継続指示を受け、現在は初版の統合検証を進めている。

| 工程 | 有限の範囲 | 終了条件 |
| --- | --- | --- |
| 1. 取得と入口の実測 | 利用中クライアントの通常TL・ブックマーク画面・単独投稿、各少数例。本文/URL/翻訳/引用/スクロールとアイコン開閉を確認 | 取れる項目と拒否するケースを記録。画面が使えない場合はそこで止め、別クライアント成功で代用しない |
| 2. 保存と探し直しの土台 | パネル、明示収集、選択保存、メモ、重複処理、通常検索、削除、書き出し・復元 | ブラウザ再起動後も保存が残り、削除・復元できる。通常閲覧中に収集・保存・新用途のAPI送信が起きない |
| 3. 目的で拾う・探す | 共通のScore判定、バッチ、進捗、中断、失敗時の表示 | 時刻のない投稿も対象。関連語が一致しない例を含め、本人の探し物で有用な結果が出る。送信件数・遅延・費用を実測 |
| 4. 過去投稿とつなげる | 1投稿対保存投稿の関係判定、原文比較、日付表示 | 無関係・不明を選べる。同名の別製品や似た宣伝文で誤って変更を断定しない |
| 5. 統合確認 | 利用中クライアントで3つの流れ、JST回帰、再起動、SPA、失敗時 | 対象コミットと実際に読み込んだビルドを確認して受け入れ記録。自動テスト通過と実画面確認を分けて報告 |

レビューで重大な問題が出た場合は、その工程内で修正・対象再テストし、未解決のまま次へ進まない。既存の `npm run check` と関連するブラウザチェックを使う。新しいテストフレームワークは追加しない。

## 完成判定案

- 拾う・保存する・探す・つなげるが、普段使っている同じクライアントで一連の操作として完了する。
- 初回は少数の固定例から始める。実利用で集まった100〜200件を最終評価の目標規模とし、5つの探し物に対して本人が期待する投稿を確認する。少なくとも4つで期待した投稿が上位5件に入ることを初期目標とする。関連がない探し物でも候補を断定しない。これは未測定の目標で、達成済みの性能ではない。
- 関係判定は明確な関連・変更・無関係・判断不能を含む小さな固定セットで確認。本文以上の事実をUIが断定しない。
- 件数別の待ち時間とAPI使用量を記録し、普段の収集に使える範囲か本人と評価する。速度や費用の数値保証は実測前に置かない。
- 原文URLから根拠を確認できる。保存本文は取得時点のスナップショットと分かる。欠落・未処理・未検索の範囲が見える。
- 保存失敗でデータを失わず、削除済み投稿や変更前の検索結果が遅延応答で復活しない。APIキーがXへ渡らない。

## 公式資料

- [Chrome action](https://developer.chrome.com/docs/extensions/reference/api/action): ツールバーからの入口。
- [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage): 既存保存領域とアクセス制限。
- [TypeSafe Score](https://docs.typesafe.ai/primitives/score): 投稿ごとの同じ基準による関連度評価。
- [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice): 関係候補と不明の選択。

資料上の機能が存在することと、このクライアント・この投稿群で期待通り動くことは別。工程1と工程3〜5で実測する。
